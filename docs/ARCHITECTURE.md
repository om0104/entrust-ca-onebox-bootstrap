# Architecture & the device-identity API

## The one-box

```
                       ┌──────────────────────────  target VM (Oracle Linux 9 + UEK)  ──────────────────────────┐
                       │                                                                                        │
   3rd-party           │   ┌───────────────────────────┐        ┌──────────────────────────────────────────┐    │
   cert requester ─────┼──▶│  CA Gateway 3.8 container  │        │  Entrust Certificate Authority 10.2      │    │
   (mutual TLS,        │   │  rootless Podman (Quadlet) │        │                                          │    │
   :8444 /cagw/v1)     │   │  cagw.service (user, linger)│  XAP  │  entca.service (autologin)               │    │
                       │   │                           │──443──▶│   ├─ PKIX-CMP  :829                       │    │
                       │   │  SecurityManager connector│──829──▶│   ├─ ASH       :710                       │    │
                       │   │                           │──389──▶│   └─ XAP       :443                       │    │
                       │   └───────────┬───────────────┘        │  embedded PostgreSQL 15  (127.0.0.1:5432) │    │
                       │               │                        │  389-ds directory        (127.0.0.1:389)  │    │
                       │               │ bind mount             │  signing key ─────────────┐              │    │
                       │      /opt/eca-cagw/config              └───────────────────────────┼──────────────┘    │
                       │                                                                    │                   │
                       │   <inst>-preload.service  ── holds a `preload … pause` session ────┤                   │
                       └────────────────────────────────────────────────────────────────────┼───────────────────┘
                                                                                            │
                                                                              nShield softcard  (Security World
                                                                              on an nShield Connect / 5c / NetHSM)
```

* **One VM.** CA + database + directory + gateway. No HA. Reboot-safe: `entca.service`,
  `<inst>-preload.service`, and the rootless `cagw.service` (via user-manager linger) all come
  back without an operator.
* **CAGW ↔ CA is local.** The `com.entrust.SecurityManager` connector talks to `127.0.0.1` /
  the host FQDN on the XAP, PKIX-CMP and LDAP ports.
* **Two independent trust chains:**
  * the **ECA CA** issues end-entity certificates (what your requesters ask for);
  * a small **self-signed mTLS CA** (generated by stage 80) secures the CAGW REST endpoint
    itself. They are unrelated on purpose.

## Non-obvious things the scripts encode

| Area | Rule |
|---|---|
| OS | Oracle Linux **9** + **UEK** kernel. The engine RPM's pre-install check enforces both for `ID=ol`. |
| Packages | `net-tools` is required by the 10.2 installer (it was not by 11.x). |
| HSM | No pure module-protection path for ECA on nShield — **softcard (or OCS) + a held `preload … pause`**. Stage 60 makes that a boot service. |
| CA init | `config_authority.sh -s -f` with `SM_INIT=false`, then `init` run separately under the preload session, driven by `expect` for the softcard passphrase + Master 1/2/3 + First Officer (Entrust password rule: 8–20 chars, upper+lower+digit+special). |
| Autologin | ECA 10.2 syntax is `service autologin -enable` only. |
| systemd | Use the **stock** CA unit — drop-ins break it under SELinux Enforcing. Stages toggle `semodule -B` after init. |
| Directory schema | The 10.2 schema LDIF is `ldapmodify`-format (`dn: cn=schema` / `changetype: modify`) — applied with `ldapmodify -f`, **not** dropped into `schema/`. |
| CAGW admin identity | Certificate type **"Admin Services User Management"** (policy OID `2.16.840.1.114027.10.4`). Not "…​Administrator" (OID `…10.21`). There is no "XAP Client" type in 10.2. |
| CAGW admin role | Needs **Perform PKIX requests** + **Create user profile** + **View activation codes** (+ Change user's role). Without the first, the CA rejects CAGW's RA-signed CMP with `(-2207) EntrustProofOfRA … insufficient permissions`. Without View activation codes, the CA returns masked codes (`****-****-****`) and every enrolment fails `cagw-5501 "Authorization code contained invalid characters"`. `User Administrator` has it by default; a custom role must have it added. |
| CSR subject order | The SecurityManager connector **reverses RDN order**. Build subjects **X.500 root-first** (`CN` last): `/DC=net/DC=example/OU=CA/CN=<device-id>`. |

## The device-identity enrolment API

CAGW exposes `https://<host>:<CAGW_PORT>/cagw/v1`. **Mutual TLS is mandatory** — the caller
presents a client certificate whose subject DN is registered in `application.yml` under
`cagw.clients` (mapped to an `integrator` → `tenant` → `ca-id`). Stage 80 generates one such
identity into `secrets/cagw-client.env` for testing; issue one per calling system in production.

`GET /certificate-authorities/<ca-id>/status` → `{"status":"UP"}` with `LDAP`/`XAP`/`PKIXCMP`
all UP. `GET …/profiles` lists the profiles from `application.yml`.

### Model A — device-generated key (CSR → X.509)

The private key never leaves the device.

```http
POST /cagw/v1/certificate-authorities/<ca-id>/enrollments
Content-Type: application/json
(client cert: cn=onebox client 1,o=onebox)

{
  "profileId": "0",
  "requiredFormat": { "format": "X509" },
  "csr": "<base64 DER PKCS#10>"
}
```

```json
{
  "enrollment": {
    "status": "ACCEPTED",
    "serialNumber": "<hex>",
    "body": "<base64 leaf certificate>",
    "certificateData": { "certificate": "<PEM>", "certificateChain": ["<PEM>", "..."] }
  },
  "message": { "message": "Enrollment was successful." }
}
```

Build the CSR subject **root-first**:
`openssl req -new -newkey rsa:2048 -nodes -keyout d.key -out d.csr -subj '/DC=net/DC=example/OU=CA/CN=device-0001'`

### Model B — CA-generated key (no CSR → PKCS#12)

For devices that cannot or should not generate their own key.

```http
POST /cagw/v1/certificate-authorities/<ca-id>/enrollments
Content-Type: application/json

{
  "profileId": "1",
  "requiredFormat": {
    "format": "PKCS12",
    "protection": { "type": "PasswordProtection", "password": "<one-time P12 password>" }
  },
  "optionalCertificateRequestDetails": {
    "subjectDn": "cn=device-0002,ou=CA,dc=example,dc=net"
  }
}
```

Response `body` is a base64 PKCS#12 (CA-generated key + leaf + chain) encrypted under the
supplied password. Deliver P12 + password to the device over a secure channel; the device
imports it and deletes the P12.

**Prerequisite (one-time, per certificate definition, in ECAA):** out of the box the
Certificate Definition has **"Generate key at client"** *enabled*, and a no-public-key request
is then rejected with *"Public key not provided in request but CA policy is configured for
client side key generation"*. Uncheck **"Generate key at client"** on the target Certificate
Definition (ideally a **dedicated** cert type for Model B so Model A keeps client keygen),
commit the security policy, and re-try. Until then only `profileId "0"` issues.

### Lifecycle

* **Renew** — `POST …/enrollments` with a fresh CSR for the same subject.
* **Revoke** — `POST …/certificates/{serial}/revocations` with a `reason`. CAGW publishes to
  the CA CRL (already published in the directory). Wire this to device offboarding.
* **Get** — `GET …/certificates/{serial}`.

### Recommended production shape

| Aspect | Recommendation |
|---|---|
| Cert types | Two dedicated ECA cert types — one client-keygen (Model A), one CA-keygen (Model B) — each with its own Certificate Definition and "Generate key at client" set correctly. Map the CAGW `default` / `pkcs12` profiles 1:1 to them. |
| mTLS clients | One CAGW client certificate per calling platform; scope integrators to tenants so a platform can only enrol under its own `base-dn`. |
| Naming | Deterministic `CN` from an immutable device attribute; document the DN root-first rule in the caller's SDK. |
| Validity | Short-lived device certs + automated renew ahead of expiry. |
| CAGW TLS key | The bundle keeps `server.p12` as a file (mode 0640). For production move it to PKCS#11 or an encrypted volume. |
| Transport | Terminate the requester↔CAGW mTLS directly on CAGW — no offloading proxy — so client-cert identity reaches the `cagw.clients` matcher intact. |
